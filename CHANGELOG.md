# Changelog

All notable changes to this project are documented here.

## [Unreleased]

- **Requests can carry header lines and a body of bytes:** `RequestParts` (`with_header`, `with_bytes`, `with_text`, `content_type`, `accept`, `if_match`, `if_none_match`, `single_try`) goes to the new `Client::request_full`, and `Request` has the public fields `headers`, `body_bytes` and `single_try` beside the old ones. Nothing that existed changes: a transport written before this keeps working because `Transport::send_full` has a default that calls `send`, and `Reply` is the same.
- **Headers cannot change how a request is framed:** only `Accept`, `Accept-Language`, `Content-Type`, `If-Match`, `If-None-Match`, `X-Api-Key` and `X-Request-Id` are accepted, each once; a name is letters, digits and `-`, a value is printable ASCII of 512 bytes at most (a line break, a control character or a letter that is not ASCII is refused), 16 headers and 256 MiB of body at most. `Host`, `Content-Length`, `Transfer-Encoding`, `Connection` and `Authorization` are written by the transport only. The client and `TcpTransport` both check, the error never repeats a value (it may be a key) and `Debug` writes names and sizes only.
- **Answers come back with their headers and their bytes:** `FullReply` (`status`, `headers`, `body`) with `header`, `etag`, `text` and `into_reply`, read by `parse_response_full` (at most 100 header lines, chunked bodies put together); `TcpTransport` and `SimServer` answer it, and the default header lines (`Accept`, `Content-Type`) are not written twice when a program gives its own.
- **The project store of the server has helpers:** `project_file_path`, `Client::get_with_etag`, `put_if_match` and `delete_if_match` read a file with its tag and write or remove it from the version it was made from; a write is sent once because the first try may have been applied. `etag_header` and `parse_etag` make and read the quoted tag.
- **The rule of the tag has errors of its own:** `StoreError::{PreconditionRequired, PreconditionFailed, Other}` for the `428` and `412` refusals, with `text(lang)` in eight languages, `code()` and `is_conflict()`; `ClientError::is_precondition_required` and `is_precondition_failed` recognise them on a plain request.
- **The server in memory simulates the store:** `SimServer` answers `GET`, `PUT` and `DELETE` of `/api/v1/apps/<app>/projects/<id>/files/content` with the `ETag`, `If-Match`, `428`, `412`, `201` for a new version and `200` with `unchanged` for the same bytes, by role; `write_file` makes a tag stale like another editor, and `set_require_if_match(false)` turns the rule off like the server's switch.
- **The table of errors has all 151 codes of the server in eight languages:** the 36 added for the laser (`laser_*`, `air_assist_off`, `enclosure_open`, `focus_not_checked`, `test_fire_refused`), the pick-and-place (`pnp_feeder_short`), the printers and the farm (`printer_*`, `farm_no_free_printer`, `thermal_runaway`, `heater_timeout`, `sensor_fault`, `temperature_over_limit`, `program_over_limit`), the slicer (`slice_*`, `bad_mesh`), the compatibility routes (`compat_off`, `compat_write_off`), the Gerber reader (`bad_gerber`, `unit_unknown`, `missing_layer`) and the machine state (`machine_alarm`, `jog_while_running`, `out_of_travel`) have their text; `tools/server_error_texts_extra.json` holds the texts Studio has no row for yet and `tools/gen_server_errors.py` prefers a row of Studio and refuses a row of the file for a code the catalog no longer has.
- **The table is tested against the catalog:** one test checks that every code of the sibling server has a text in the eight languages and one that the new codes keep their status, are not the English text in another language and the Portuguese is the one of Portugal; both are skipped when the server repository is not next to this one.
- **The settings panel lists the open sessions:** `SessionsView` reads `GET /auth/sessions` (the one in use first), closes another session and reads the list again, and asks "are you sure" before closing the session in use, which logs the person out; new `Action`s (`OpenSessions`, `HideSessions`, `RefreshSessions`, `CloseSession`, `ConfirmCloseSession`, `CancelCloseSession`) and a notice for a closed session. A failed reading keeps the last list and says why; a person who is not logged in has no list.
- **A link badge any window can reuse:** `LinkBadge` (`observe`, `all`, `label`, `tone`, `hint`, `tooltip`, `is_alert`) is a dot and a word for the state of the link with what the person can do about it, and `server_gui::link_badge` draws it with egui 0.37; the panel now uses it for the state line and shows a Sessions button and the list.
- **13 new words in the eight languages:** the sessions (list, refresh, hide, none, close, this session, closed, the warning about the session in use, yes, application, address, role) and the word for the link, in English, Spanish, Italian, German, French, Portuguese (Portugal), Chinese and Japanese.
- **More tests, some on many inputs made with a fixed seed:** random headers never pass with a line break and the head of a request has exactly the lines it should, a tag comes back as it went, the names of files make one safe query, bytes written from the right tag come back whole and a stale tag always conflicts, and the reader of answers never panics on damaged text.
- **The client guide has the migration steps app by app:** `docs/SERVER_CLIENT.md` says how the program that still has its own transport retires it and what the others do when they save into the store, and explains the headers, the bytes, the tag rule, the sessions and the badge.

## [0.2.5] - Server settings panel in eight languages, optional mDNS, offline queue, contract cache and link metrics

- **Every machine program can show the settings of the server in the same way:** `eh3d_view::server_panel` is the settings panel as a model with no window in it: `ServerForm` (the six boxes `server_address`, `server_token`, `server_machine`, `server_timeout_s`, `server_retries` and `server_mdns`, checked against the same ranges as the client plus the shape `host:port`; the saved token is never copied into the form, a new one is typed into a write-only box and the saved one can be removed), the state of the link (connected, disconnected, session expired, no session, not checked yet, no server set), the login window (the password is wiped from memory as soon as the call is made) and `ServerPanel`, which does what a window asks and gives the settings to save when they are applied. Tested against `sim::SimServer`: a good login, a wrong password, a session that runs out, a logout, a server that goes away and comes back, no address and a bad box.
- **Failures of the client in the language of the person:** `server_panel::error_text` gives the text of the code of the server, or the sentence of the kind of failure with the number of tries, and the settings the client refuses (no address, no machine, searching the network off, no resolver) have their own words.
- **The words of the settings of the server in the eight languages:** `eh3d_view::server_texts::ServerText` has 38 texts in English, Spanish, Italian, German, French, Portuguese (Portugal), Chinese and Japanese (a row with a missing value does not compile); a variant speaks its main language and the other languages English until they are translated. Tests check the eight values, the markers, the letters of Chinese and Japanese, the Portuguese of Portugal and that no text is left in English.
- **A panel for the settings of the server drawn with egui:** the new feature `gui` of `eh3d-view` (off by default, egui 0.37) adds `server_gui::show`, which draws the boxes, the state of the link, the login window and the notices over that model and gives back the action chosen. The CI compiles it in a job of its own that does not decide the result of the run.
- **The server can be found on the local network, if the owner turns it on:** the new feature `mdns` of `eh3d-serverclient` (off by default, no dependency) adds `mdns::MdnsResolver`, a small multicast DNS client over UDP that asks for `_eh3d._tcp` and reports only what the network says: a service with a port and the address records that came with it, or the name of the host, never an invented address. The search lasts at most ten seconds, reads at most 64 packets of 9000 bytes and 128 records each, follows a name pointer at most sixteen times, ignores goodbyes and keeps at most 32 services; `Client::with_mdns()` gives it to a client, and `server_mdns = off` still means that nothing is asked of the network. Tested against a responder on the loopback, a hostile answer, a flood of records, cut and damaged packets and the time limit.
- **How the server announces itself is written down:** `docs/SERVER_CLIENT.md` has the card of the announcement (service type, instance name, port, host and address records, TXT keys, times to live, goodbye and unicast answers) and an Avahi file for the CM5; announcing is for the server to do and stays off unless its own setting is on.
- **Requests that cannot be sent wait for the server:** `OfflineQueue` keeps the `PUT` and `DELETE` requests that failed because the server was away (never a `POST`, never a `GET`), bounded in number, in the size of each body, in the size of all of them and in age, refuses with the reason (`Rejected`), keeps one request per path (the latest wins) and `Client::send_or_queue` and `Client::flush` send them in order when the server is back, stopping at the first one that cannot be sent and dropping, with what the server said, the one it refuses. Nothing is written to disk.
- **The client notices the routes the server withdraws:** `Contract` reads the routes of an OpenAPI document (a `{name}` segment matches any one segment), `ContractCache` keeps the newest contract and the routes that an earlier one had and the newest does not, `Client::refresh_contract` updates it and `cache.status` says whether a route is known, retired or unknown before a program relies on it. The cache is kept in a text file between runs and a damaged file is refused whole.
- **Metrics of the link:** `Client::metrics()` counts requests, tries, retries, answers, 5xx answers, losses and disconnects and gives the last, smallest, largest and mean latency and the median and the 95th percentile of the latest 128 answers, with `to_text()` for a log; it holds no token, body or address.
- **More tests, some of them on many inputs made with a fixed seed:** the JSON reader never panics on random or damaged text and refuses deep nesting, a name in a path cannot change where the request goes and comes back whole, the settings written and read again are the same and a value out of its range changes nothing, the pauses between tries never shrink, the queue keeps its limits whatever is done to it, the contract cache never calls retired a route the newest contract has, a `GET` is tried once more for each retry allowed and no more, and a `POST` that may have been sent is never sent again.
- **The CI also checks the optional resolver:** `rust.yml` runs clippy and the tests of `eh3d-serverclient` with the feature `mdns`, and a job that does not decide the result compiles the panel of egui.
- **The README counts the tests as they are:** 604 `#[test]` (60 in the main crate and 544 in the shared crates), the 124 of the client and the 81 of the interface crate, in the eight languages, and it names the new pieces of the client.

## [0.2.4] - The one client of the EH3D server: login, refresh, sessions, retries and errors in eight languages

- **One client for every program that talks to the EH3D server:** the new crate `eh3d-serverclient` (no dependency, no window) logs in with `POST /auth/login` for the application the program is, renews the login with `POST /auth/refresh` (by itself when it is in its last quarter), ends it, lists and closes sessions, checks `GET /health` without a token and sends any route with the bearer token. The state of the link is `Connected`, `Disconnected` or `LoggedOut`. `docs/SERVER_CLIENT.md` describes it and gives the steps for each program to move to it.
- **The keys of the link have one reader, with ranges and conservative defaults:** `server_address`, `server_token`, `server_machine`, `server_timeout_s` (1 to 120, 15 by default), `server_retries` (0 to 5, 2), `server_mdns` (off) and `server_max_answer_mib` (1 to 256, 8). A value out of its range names its key and line and changes nothing.
- **Retries with growing pauses, and a `POST` is never sent twice:** a failed connection is tried again for any method; a time-out or a broken connection only for the methods that can be repeated; the pauses are 200 ms, 400 ms, 800 ms up to 2 s. When the tries run out the error says how many were made and the login is kept.
- **The token cannot be printed by mistake:** `Secret` writes `***` in `Debug` and `Display` and overwrites its bytes when dropped; `TokenStore` decides where it is kept (memory by default, or a file only its owner can read); a 401 makes the client forget it everywhere.
- **The refusals of the server by code, with their text in eight languages:** `ClientError::text(lang)` gives the text of the code in English, Spanish, Italian, German, French, Portuguese (Portugal), Chinese or Japanese from a table generated by `tools/gen_server_errors.py` from the error catalog of the server and the texts of the studio; a code the table does not know is shown as itself. A test compares the table with the catalog of the sibling server and is skipped when it is not there.
- **Discovery of the server on the network is optional and off:** `server_mdns` is `off` by default, the client asks nothing of the network while it is off, and a resolver is given by the program that wants it.
- **A server that lives in memory for the tests of every program:** `sim::SimServer` logs in, renews, closes sessions, refuses with the codes of the catalog and fails on demand (no connection, time-out, 503) with a clock and a sleeper that make time pass without waiting.
- **The README counts the new crate:** 493 tests, the fifteenth shared crate, and a link to the new guide, in the eight languages.

## [0.2.3] - True orthographic standard views

- **The standard views of the machine, with a true view from above:** `eh3d_view::views` adds `StandardView` (`Top`, `Front`, `Side`, `Iso`) and `Ortho`, which projects a point of the machine to a pixel with the same scale on both axes (from above X to the right and Y up with the height ignored, from the front X to the right and Z up, from the side Y to the right and Z up, and the usual isometric one), `Ortho::to_table` for a click on the plan, `Ortho::fit_box` and `Ortho::fit` to centre a box of the machine in an area with a margin, `StandardView::orbit_angles` (front 315 and 0, side 225 and 0, isometric 0 and 30) and `Iso::standard`. Nothing existing changes: `Iso` keeps its fields and its projection, and a test holds the numbers of the default view. Ten tests cover known points, the axes, the height, the fit and the click.

## [0.2.2] - Drill units that say if they were declared, limits for the drill reader and the GRBL link, and a stop that reaches a busy controller

- **The status report that arrives while a line waits for its `ok` is kept:** the `UrgentChannel` of the controller holds the last report that answered an `Urgent::Status`, and `take_report` hands it over once, so a program can show the live position of a machine that is busy with a line.

- **A drill file says whether its unit was declared:** `DrillFile::units_declared` is true when the file has `METRIC`, `INCH`, `M71` or `M72` and false when the numbers were read as mils for lack of a header, so that a program can warn that the unit was supposed. Tested with files with each header, with only `;FILE_FORMAT=` and with none.

- **The drill file reader has limits of its own and keeps the lines it leaves out in bounds:** `ncd::parse` refuses a file past the hard limits of the shipped `reader_limits.cfg` (64 MiB or 4 million lines, the values a program can replace with its own copy through `parse_limited`, which no longer applies the default limits on top) with a new `ParseError::TooLarge`, and keeps only the first 10000 lines it leaves out (slots and tool up/down moves) in `DrillFile::ignored`, counting the rest in the new `ignored_more`. A file larger than the limits that `parse` used to read is now refused. Tested with a file of too many lines, with a flood of slot lines and with wider limits of its own.

- **A GRBL controller that restarts by itself in the middle of a program is noticed:** the greeting a GRBL prints when it starts (`Grbl 1.1h ['$' for help]`) used to be skipped like any other message, so a restart between two lines (a power dip, a noisy cable, its button) let the sender go on with cutting moves and the spindle off. The line, status and busy waits now read a greeting that the program did not ask for (no reset of its own is waiting for one) as a refusal, which stops a program. The greeting that follows a reset the program sent, from the sender or from another thread, is only consumed. Tests cover a restart between two lines, in the status, and the greeting after a reset of ours.

- **The README counts the files of the firmware base as they are:** 118 files, 68 of them shared by the two touch screens, as the manifest of `firmware_base/` lists them.
- **The two touch screens share the stop as a flag, the plan of its retries and the rule of what is sent to an address that is not a server:** `core/stop_latch.hpp` (new; the flag a stop sets and the task of the stop takes, `stop_retry_after`), `may_send` and `is_stop_order` in `core/server_link.hpp` (after a health check that found nobody or something that is not an EH3D server only the health check and the stop go out), the settings `stop_retries` and `stop_retry_ms`, and the verdict kept by `main/server_link.cpp`; the copies in both screens are the same and the host tests cover them. The firmware base is now 118 files.
- **A stop, a hold or a reset reaches a controller that is busy waiting for an `ok`:** `Controller::urgent_channel()` gives a handle (`UrgentChannel`) that another thread keeps; what it puts in (`Urgent::Reset` `0x18`, `Hold` `!`, `Resume` `~`, `Status` `?`, and `StopJob`, the hold followed by the reset) is written to the machine within a few milliseconds, without waiting for the `ok` of the line in progress and without queueing behind lines. GRBL looks at the channel every 25 ms while it waits (a reset or a stop ends the wait with an error, a hold lets the line go on waiting), and before every order; the simulated machine applies it before anything else. `GrblController::with_busy_limit` sets how long a line waits while the machine says it is working. Tests against the simulator and against a link in real time. Simulation only: nothing has run on a real board.
- **The shared firmware base reads the whole numbers of the server within a range:** `Json::int_in(key, lo, hi)` brings a number of the answers of the server into range before it becomes an integer (a value such as `1e99` is no longer converted as it is), with a host test; the copies in the screen projects are the same.
- **A `;FILE_FORMAT=` line with an absurd count of digits no longer exhausts the memory:** the Excellon reader takes only 1 to 6 digits on each side of the point (any other line is ignored) and caps the zero padding, so a four-line drill file cannot ask for a string of billions of characters; a test covers the huge, the zero and the overflowing counts.
- **The shared firmware base follows the touch-screen projects again:** the copy of the stop of the machine, the health check without the token and the other changes made in the screen projects since the last import are in `firmware_base/`, so the check of the copies passes.
- **Faults of the link with a GRBL board, tried against a twin of the board:** add `crates/controller/tests/link_faults.rs`, a board in memory that answers `ok`, `error:N`, `ALARM:N` and the status report and fails by plan (a reply that never comes, a line of noise, a refusal, an alarm, a cut link) or by a seeded generator. Seven tests cover the timeout and the feed hold, the refusal with its number and the text of the manual, the alarm that locks the board until `$X`, the cut link that works again once mended, the emergency stop that needs no answer and a seeded run of every fault that is the same every time. Nothing has run on a real board.

- **The shared validation tools are updated:** the validator also runs the workflow and lessons checks of the suite with their latest rules, including a check to run before every push.
- **The CI validation checks the workflows and the lessons of past CI failures against a baseline:** `tools/workflow_hygiene.py` and `tools/lessons_lint.py` (copies of the shared tools) run in the validation, and only findings that are not in `tools/workflow_hygiene_baseline.json` and `tools/lessons_lint_baseline.json` fail it, so what exists today stays as it is and a new one is caught. `python tools/workflow_hygiene.py --root . --detail` and `python tools/lessons_lint.py --repo .` list the findings.
- **The validation of the CI is the reusable one of the documentation hub:** the job `validate` calls `validate.yml` of EH3D-DOCS (pinned by commit) and what the repository checks besides it is in jobs of their own, with the check of the CHANGELOG.
- **The CI is split in two workflows:** the validation of the repository (manifest, documentation, pictures, tools) stays in `ci.yml` and the Rust jobs move to `rust.yml`, which does not run for a change that only touches the READMEs, the CHANGELOG or pictures, so a change of the documentation no longer builds the code on two systems, and they keep a cache of the build. The names of the jobs are the same.

## [0.2.1] - Typed archive errors, reader limits, shared spindle table and the firmware base guards

- **A pull request must say what it changes:** the validation runs `tools/changelog_pr_check.py` on a pull request (it fails when the CHANGELOG has no new line under [Unreleased]; the label `no-changelog` skips it), the same check as the other repositories of the suite.

- **The settings file of the screens is tested damaged:** `firmware_base/tests/test_hmi.cpp` reads the settings file cut at every place and in 600 copies with bytes changed, inserted or cut (a fixed seed), and no value ever leaves its range.

- **Two property tests of the firmware base with a fixed seed:** the scanner of the board mark is checked against a plain search over 400 images of random bytes with the mark planted at a random place (read in pieces of random sizes), and the heartbeats of the guard against a plain model over 2000 looks.

- **The two touch screens share one `core/`:** `hmi_config.hpp` (with the panel that moves the machine by hand and the kind of machine), `gate.hpp`, `keyboard.hpp`, `status.hpp`, `ui_text.hpp`, `locales.hpp`, `machine.hpp`, the 30 files of `locales/` and the generated `locales_gen.hpp`, `font_ranges.hpp` and the two fonts (`main/fonts`) are base files now, in their union: what one screen does not use the other leaves alone. The fonts are built in GitHub Actions from the literals of both screens (`EH3D_EXTRA_LITERALS` in `tools/make_locales.py`), so both carry the same glyphs. The firmware base is now 117 files, 67 of them shared by the two screens.

- **Seeded fuzz tests of the readers:** `crates/formats/tests/fuzz_seeded.rs` gives the readers of the drill file, the plot, the drawing and the Gerber outline ten thousand texts made from a fixed seed (pieces of real commands glued at random, cut at random, with random bytes) and checks that none panics, and gives the limited readers five thousand more to check that a text past a hard limit is always refused with `EH3D-FORMATS-011` and that both the warning and the refusal are reached. Two tests.
- **The rule that picks what a job works on is shared:** `eh3d_bungard_formats::selection` (`vector_range`, `panel_offsets`, `inside_work_area`) holds the range of vectors, the copies of the board on a panel and the test of the working area as plain functions, so the drilling, the routing and any other program that plans a job apply the same rule. Three tests check the range, the grid and the edges of the working area.
- **The firmware base watches the heartbeat of the tasks, checks the board of an image and the subsystems of a new one, and the screens confirm their image:** `core/node_guard.hpp` has `find_stalled` (a task that is there but whose count of beats has not moved for 30 seconds is trouble like a missing one), the bits `kSub*` and `image_may_be_confirmed` with the subsystems a node needs, and the new `core/board_mark.hpp` (the `EH3D-BOARD-MARK:<board>` an image carries and the scanner that reads it back, refusing an image made for the other board); `main/node_guard.cpp` adds `beat`, `subsystem_up`, `image_board_ok` and the line about a core dump left by the last crash. The two screens share `main/image_confirm.hpp` (an image written by an update is confirmed after 30 seconds of running and goes back at once when the display does not start) and `core/server_link.hpp` has the health check of the server (`health_request`, `classify_health`). The settings header the shared files include is `core/node_config.hpp`. The two screens also share `core/ops.hpp` (the orders of the screen as an enum, with the id of each one and a test through the whole table). The firmware base is now 74 files.

- **The guide to use the crates says how a tag is pinned, what `min_common` is and where the limits are kept:** `docs/CONSUMING.md` names the current tags, explains when a repository keeps the sibling at `main`, the optional `min_common` of the manifest (the oldest version it works with, which only goes up) and the files that hold the limits of the readers and of the spindles.
- **One table of spindles for the whole suite:** `eh3d_materials::spindle` (`IDS`, `Limits`, `defaults`, `from_table`) holds the limits of the two spindles a machine can carry (turns, power, feeds along the cut and of the plunge, and the thickest bit), read from `crates/materials/spindles.cfg` instead of being written in the code, so that the server and the interface of the machines judge a job against the same numbers. Three tests check the shipped table, a line that cannot be read and the limits that cannot be used.
- **A big file is said in the 37 languages, and a refusal comes in the language of the screen:** the new text `WarnBigFile` (all the languages of the project), `eh3d_summary::summary::size_warning` (the notice for a file that a reader accepted past a warning limit), `join_warnings` (the notices of a loaded file as one line) and `refusal_message` (a `FormatError` with its code and its words in the language of the screen), so the programs that call `ncd::parse_limited` and `hpgl::parse_limited` show the same notice. Two tests check every language and the refusal.
- **The readers of the Gerber outline tell their errors with a code, and the readers refuse a file past the limit:** `gerber::outline_checked` gives `EH3D-FORMATS-008` (no format statement), `-009` (no outline) and `-010` (a coordinate that cannot be read) as a `FormatError`, and `gerber::outline` keeps its text error (it now starts with the code). `ReaderLimits::guard` turns a file past the hard limits of `reader_limits.cfg` into `EH3D-FORMATS-011`, which `gerber::outline_checked`, `dxf::outline_checked` and `hpgl::parse_strict` apply with the shipped values, and `ncd::parse_limited` and `hpgl::parse_limited` apply with the limits of the program and say when the file is past a warning limit, so that a program can tell the user.
- **Limits for the readers, kept in a configuration file:** `eh3d_bungard_formats::limits::ReaderLimits` refuses a text file with more bytes or lines than the hard limits and tells a program when a file is past the warning limits (`check`). Three tests check the shipped values, the three verdicts and the refusals of a bad configuration.
- **The archive reader tells its errors by kind:** `eh3d_archive::ArchiveError` (`Io`, `Zip`, `TooManyEntries`, `NotInArchive`, `TooBig`, `UnsafeName`) replaces the text errors of `Archive::open`, `read`, `read_limited` and `extract`; its words are the same as before, and `String::from(error)` keeps callers that carry their errors as text working. A test checks each kind and the conversion.

## [0.2.0] - The build text of a program, the file tree check in the validator, formats with error codes and a Paper theme that reads well on every surface

- **The Paper theme reads well on every surface:** the colours of the OK, warning and second accent inks and the dim text of the light theme are a little darker (`#166534`, `#92400e`, `#9a3412`, `#545c6b`), so that every ink has a contrast of at least 4.5 on the panel, on both ends of the background, on the table and on the board; a new test checks every ink against every surface. Tests: 372.
- **The build text of a program:** the new module `eh3d_common::build` (`BuildInfo`, `BuildKind`, `BuildError`) is the small JSON text that a program carries inside its binary to say which build it is (`{"schema":1,"repo":...,"version":...,"commit":...,"kind":"release"}`), without a file beside it, the network or the clock. `embedded_build!()` makes it when the program is compiled from the version of the crate and from `EH3D_BUILD_REPO`, `EH3D_BUILD_COMMIT` and `EH3D_BUILD_KIND`; `BuildInfo::from_json` is a strict reader (one flat object, no key twice or unknown, no escapes, at most 1024 bytes) whose refusals have the codes `EH3D-BUILD-001` to `EH3D-BUILD-008`, and `to_json` always writes the same bytes for the same record. ## [0.0.1] - The project container, its metadata and the machine telemetry types

- **The `.eh3dproj` container:** a ZIP archive with `project.json`, `integrity.json` and the folders `layers/`, `toolpaths/` and `vision/`. The writer is deterministic and writes through a temporary file.
- **Integrity:** the SHA-256 and the size of every entry are recorded; a package with a changed, missing or unlisted entry does not open.
- **Limits:** entry names that could leave the package folder are refused, and so are oversized or too many entries.
- **Metadata:** name, identity, units, zero of the workpiece, layers, tools, toolpaths and fiducials, validated, with a semantic format version: a newer major version is refused and an older one needs a registered migration (there is none yet).
- **Telemetry types:** axes, spindle, machine states and GRBL alarm codes with their severity.
- **Theme:** the colours of the suite with a contrast check.
- **Firmware base of the nodes:** `firmware_base/`, the part of the ESP32 node firmware that every EH3D node shares (settings, network, panel server, users and sessions, update with rollback, log, self-protection, tests), written once with the project's name as placeholders, and `tools/sync_firmware_base.py` to write it into the nodes and check the copies. CI runs the check.
- 29 tests, `cargo clippy -D warnings` and `cargo fmt --check` in CI on Linux and Windows, and a repository check of the manifest, the versions, the changelog and the eight README files.
